# Math Quest: rules for working on this repo

A kids' math game (Cloudflare Worker + one self-contained web page). Progress saves in the browser and, optionally, to
accounts in Cloudflare KV. Read this before changing anything.


## How to work (read first)
Behavioral guidelines to reduce common LLM coding mistakes (from the Karpathy-skills rules). They bias toward caution over speed; for trivial tasks, use judgment.

### 1. Think Before Coding
Don't assume. Don't hide confusion. Surface tradeoffs. Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First
Minimum code that solves the problem. Nothing speculative.
- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it. Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes
Touch only what you must. Clean up only your own mess.
- Don't "improve" adjacent code, comments, or formatting. Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.
- Remove imports/variables/functions that YOUR changes made unused; leave pre-existing dead code unless asked.
- The test: every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution
Define success criteria. Loop until verified. "Add validation" -> write tests for invalid inputs, then make them pass. "Fix the bug" -> write a test that reproduces it, then make it pass. "Refactor X" -> tests pass before and after. For multi-step tasks, state a brief plan:
```
1. [Step] -> verify: [check]
2. [Step] -> verify: [check]
```

### 5. Use existing code first (this repo)
Before writing anything, search `src/` for a helper, constant, pattern or similar feature and reuse or extend it (see "Reuse before writing"). A new helper or a second copy needs a one-line reason in your reply.

### 6. Save tokens (this repo)
Use the file map below and the area rules in `.claude/rules/` (they load when you open matching files) instead of exploring. Never read `worker.js`, `package-lock.json` or `art/` (generated or binary). Read only the part of a file you need (offset/limit or grep), not whole big files.

## Layout and build
- **Edit `src/`, never `worker.js`.** `worker.js` is generated by `npm run build` and is committed on purpose (so the
  game can also be pasted into the Cloudflare dashboard). CI fails if it is out of date: run `npm run build` and commit it.
- `src/client/index.html` (page shell), `src/client/styles.css`, `src/client/js/NN-name.js` (joined in filename order into one
  `<script>`; top-level `const`/`let` must be declared before use at load time, functions can be used anywhere).
- `src/shared/econ.js` is included in BOTH the browser script and the Worker. `src/server/NN-name.js` is the Worker.
- Client code is plain JS written normally. No template-literal escaping tricks. The build syntax-checks it and fails on errors.
- No dependencies, no external network requests, no fonts or scripts from other sites (the CSP forbids them).
- The service-worker cache name is derived from the build hash automatically. Never bump a version by hand.

## Commands
- While you work: build + lint run after each edit of `src/` (hook, silent when fine) and the tests for the files you changed run when you finish (Stop hook, skipped if nothing changed since the last green run). Fix what they print; never skip or weaken a test.
- `npm run test:quick` runs build, lint and only the tests covering your changed files (one line when green). `node --test tests/x.test.mjs` runs one file. Prefer these.
- `npm test` builds, lints, then runs every test (about 3 minutes); CI runs it on every PR. Run it yourself only when you touched shared things (`econ.js`, `03-state.js`, `10-save-load.js`, `styles.css`, `index.html`, `30-router.js`, `build.mjs`) or before a big commit.
- `npm run lint` checks the browser script and the Worker for calls to functions that do not exist and for page handlers with no function behind them (an earlier refactor silently deleted `hubStep`). `npm run check` verifies `worker.js` is current.
- A change that touches what players see needs a test, not just a screenshot. In the cloud sandbox Playwright's Chromium is already installed; do not run `playwright install`.

## Reuse before writing (most important rule)
Search the codebase first. Never write a second copy of something that exists. Existing helpers:
- Dates: `dayKey(d?)`, `daysAgoKey(n)`, `lastDayKeys(count, skip)`. Do not hand-roll date strings.
- Modals: `showModal(id, before)` / `hideModal(id, after)`; give the overlay `data-close="fn"` (tap + Escape) or `data-esc="fn"` (Escape only, for game screens). No per-modal `…OnOverlay` functions.
- Rewards: `grantGems(n, message, big)` for any payout that celebrates. Costs/rewards/limits live ONLY in `ECON` (`src/shared/econ.js`).
- Questions: `makeMcq({op, problem, count})` + `fillOptButtons()` for every multiple-choice screen (battles, signs, duels). Battles use `abQuestion()`.
- Buddy gear: every accessory has a `slot` (head, face, neck, back, side, aura); positions come only from `GEAR_SLOTS` in `08b-buddy-gear.js` and are used by the battle screen, hub and trading card. Never add per-item pixel offsets in CSS. Armor is the corner badge. New gear needs no CSS.
- Text safety: `escHtml()` for anything a user typed or the server sent, before it goes into `innerHTML`.
- Saves: `saveState()` (never `localStorage` directly), `addXpTo(id, n)` for buddy XP.
- Question difficulty: which type and level the next problem uses is decided only in `07b-adaptive.js` (`pickNextProblem`, `recordAdaptive`, `typeShares`); numbers are in `ECON.adaptive`. Levels follow recent accuracy and speed per type, never the combo streak. Tournaments, duels and the vault use `makeMcq`, which ignores levels on purpose (fair for both players).
- Stakes: `stakeAllowed()` / `allowedStakes()` (shared with the server).
- If the same shape of code appears a second time, extract a helper in the right file instead of pasting.


## Saved state
- Every new field gets a default in `freshState()` (`03-state.js`). Loaded saves go through `normalizeState()`: add a small function to `NORMALIZERS` for clamping or repairs.
  Never trust data from localStorage or the cloud.
- If a field changes shape, bump `SCHEMA_VERSION` and add a `MIGRATIONS` entry. Keep saves small (`ECON.save` limits; `pruneState()` trims history).
- Never store secrets in the save.


## Players and play
- This is a Pokemon Gold style adventure that stays friendly to young players: no chat, no free text shown to other players, no personal data, no tracking or analytics. Player names only.
- Stakes in duels may only ever be gems, never levels, XP or buddies. Keep a free option. Gems never go below zero.
- There is no parent dashboard or Practice screen: the Adventure map is the whole game (see `.claude/rules/battles.md`).


## Git
- Work on the branch you were given. Commit messages: short imperative summary, then the attribution lines the session asks for.
- Do not open a pull request unless asked. Do not force-push. Do not commit `node_modules/`.
- Keep commits focused: one feature or fix, with its tests and the rebuilt `worker.js`.
